## 1. 一句话定义（MVP）

**在屏幕上框一块区域，实时 OCR 出里面的字幕，在右侧悬浮窗以滚动字幕的形式显示，全程落盘，最后导出中英对照纯文本。**

不控制任何播放器，不依赖任何平台的接口，纯粹是"屏幕层面的 OCR"。因此**理论上对任何软件、任何网页、任何网盘都成立**。

## 2. 功能需求（全部 P0）

| 编号 | 功能 | 说明 |
|---|---|---|
| **M1** | 框选区域 | 拖拽框出屏幕上的字幕区域；结果持久化，下次自动应用 |
| **M2** | 实时 OCR | 定时抓取该区域并识别；画面未变化时跳过，避免空转耗电 |
| **M3** | 中英分行 | 同一条字幕的英文行与中文行配对成一组 |
| **M4** | 翻译兜底 | 若某组只有英文没有中文，调用翻译补上 |
| **M5** | 悬浮窗字幕稿 | 置顶悬浮窗，按时间顺序滚动显示；当前句高亮；可上下翻回看 |
| **M6** | 落盘 | 每条字幕（时间、原文、译文、来源）持久化 |
| **M7** | 导出 | 一键导出中英对照纯文本（Markdown / txt） |
| **M8** | 会话重命名 | 工作台侧栏双击或右键改会话名；名字是展示名，**不动目录**（v0.3） |
| **M9** | 句子收藏 | 句子上打星标，落盘到会话目录的 `favorites.json`；跨会话聚合展示；可导出成一篇文章（v0.3） |

### 关键设计点

**M3 中英配对**：同一帧里识别到的行，按 boundingBox 的 y 坐标排序。检测到中英各一行 → 配成一组；只有英文 → 触发 M4。若视频用的是"中英分开的两行字幕"，这个规则就够用。

**句子的起止**：硬字幕没有时间轴。用"**连续 N 帧文本相同 → 确认成句**；文本变空或变化 → 上一句结束"。相邻帧用 Jaccard / 编辑距离去重，避免同一句反复入库。

**M5 是产品的灵魂**：硬字幕一闪而过，悬浮窗的价值是**可回看上下文**——这是"看得爽"和"学得进"的分水岭。

**M7 几乎是白送的**：M6 已经在积累全量字幕，导出只是换个序列化格式。

**M9 的落点不是"标记"，是"攒出一篇能背的东西"**：收藏单独存 `favorites.json`，**不进 `entries.jsonl`** —— 后者是追加写、崩溃安全的设计，工作台改写它会破坏那个前提。收藏记录自带中英文本快照，于是跨会话的收藏视图只需读 N 个小文件，不必解析 N 份完整字幕稿。

**M8 只改展示名**：会话目录名（= id）是排序键兼引用目标，改名不动它，只写 `meta.json`。代价是**已经导出过的文件不会追溯更新**——下一次导出才用新名字。

## 4. 技术选型

| 项 | 选择 | 说明 |
|---|---|---|
| 语言 / UI | **Swift 6 + SwiftUI** | 本机已具备：Swift 6.3.3、SDK 26.5、macOS 26.5.1 |
| 抓屏 | **ScreenCaptureKit** | 系统原生，可精确指定捕获区域 |
| OCR | **Apple Vision（`VNRecognizeTextRequest`）** | 本地、免费、离线、无模型依赖 |
| OCR 等级 | **`.accurate`（强制）** | `.fast` **完全不支持中文** |
| 悬浮窗 | **`NSPanel` + `.nonactivatingPanel` + `.fullScreenAuxiliary`** | 能同时做到置顶 + 不抢焦点 + 跨 Space + 覆盖全屏 |
| 本地存储 | SQLite 或 JSONL | 数据结构简单 |
| 构建 | **SwiftPM + 打包脚本** | 本机**未安装 Xcode**（只有 CLT）。`swift build` 出可执行文件，脚本生成 `.app`。**已用 spike 验证可行** |
| 翻译 | **Apple Translation framework** | 本地、免费、离线、零配置；**接口做成可替换**，以后可换 LLM |

### 构建方式（已定：SwiftPM + 打包脚本）

本机 `xcodebuild` 不可用（只有 CLT），所以走 **SwiftPM**：`swift build` 出可执行文件，再用脚本生成 `.app` 目录结构 + `Info.plist`。**不用装 Xcode。**

已在 `spike/` 里验证：纯 SwiftPM 包能正常 import ScreenCaptureKit / Vision 并编译运行。

**开发期的一个注意点**：屏幕录制权限绑定代码签名，**ad-hoc 签名的权限每次重新编译都会被丢失**。需要在"钥匙串访问"里建一个自签名证书，让签名身份稳定 —— 否则每次改代码都要重新授权。

**运行期权限的归属**：从终端 `swift run` 时，系统把屏幕录制权限记在**终端 App** 头上（Terminal / iTerm / VS Code）。spike 已验证这个行为。

## 5. 关键技术事实（调研结论，仍然适用）

**① 中文 OCR 必须 `.accurate`，帧率锁定个位数 fps**
实测 100–300ms/帧。字幕每句持续数秒，**2–5 fps 完全够用**。架构上把 OCR 放后台队列 + 时序去重即可，**不要按 60fps 设计**。

**② 中英混排的正确写法**
```swift
let req = VNRecognizeTextRequest()
req.recognitionLevel = .accurate                          // 中文强制；fast 不支持中文
req.recognitionLanguages = ["zh-Hans", "zh-Hant", "en-US"] // 中文必须排在前面
req.usesLanguageCorrection = true
req.customWords = ["角色名", "专有名词"]                    // 提升专名准确率
```
限制：**English 是唯一能与中文配对的语言**；**`automaticallyDetectsLanguage` 对中文无效**，必须显式指定。每行返回 `boundingBox`（归一化、**左下原点**，需翻转 y），用它做中英分行。

**③ 悬浮窗会被自己录进去**
ScreenCaptureKit 抓的是**合成后的帧缓冲**。必须用 `SCContentFilter` 的 `excludingApplications` / `excludingWindows` **排除本 App**。macOS 15+ 之后 `sharingType = .none` 已经失效，不能靠它。
（本版已砍掉遮挡功能，但**只要悬浮窗和字幕区域有重叠，这个问题就还在**。）

**④ 坐标系有三处错位**
AppKit 左下原点 / 全局坐标 vs SCK 左上原点 / 屏幕局部坐标，外加"点"与"像素"的换算。**单主屏时 bug 会被隐藏，接副屏必然暴露。**

**⑤ 网格帧率与功耗**
画面未变化时跳过 OCR（帧哈希比对），能显著降低 CPU。

## 8. 翻译方案（已定：Apple Translation）

| 方案 | 结论 |
|---|---|
| **Apple Translation framework** | ✅ **采用**。系统内置、本地、免费、离线、零配置 |
| LLM API（Claude 等） | 质量最好、可带上下文，但需 key / 联网 / 成本 → **留作以后的可替换选项** |
| 本地 LLM（Ollama） | 免费离线，但慢、占内存 → 不采用 |

**触发条件**：只在某组字幕**识别到纯英文、没有中文**时才调用；不是每句都翻。

**架构要求**：翻译层必须做成**可替换的接口**。原因是 Apple Translation 质量中等、没有上下文能力，将来很可能想换成 LLM——到时候只换实现，不动调用方。

## 9. 技术验证 spike

位置：[`spike/`](../spike/) — 一个独立的 SwiftPM 包。

**要验证的**：ScreenCaptureKit 抓屏幕一块区域 + Apple Vision 识别中英混排，能不能跑通、多快、能否拿到分行坐标。

**怎么跑**：
```bash
cd spike
swift run SubtitleSpike          # 抓屏幕底部 28% 横带
swift run SubtitleSpike --full   # 抓整个屏幕
```

**跑之前**：
1. 先让一个带中英硬字幕的视频播起来
2. 首次运行会申请「屏幕录制」权限 —— 到 系统设置 → 隐私与安全性 → 屏幕录制 里勾选你的终端，**然后重启终端**

**输出会告诉你的**：
- 有没有文字 → 抓屏正常（没黑屏）✅
- `[中]` / `[英]` 标签 → 中英识别是否正常 ✅
- `y` 值是否上下分开 → 能否把中英两行配对成一组 ✅
- OCR 耗时是否在 100–400ms → 帧率是否够用 ✅

**已确认**：编译通过、无报错、权限缺失时能正确提示并引导。

| boundingBox 分行 | 有效 | ✅ |
| 缩放系数 | **2.00x** | 修复前错算成 1.0x，见 9.2 ② |

**技术链路全部验证通过。**

### 9.2 两个必须正面解决的问题

**① 噪音淹没字幕（原以为的低风险，实测是主要矛盾）**

首次抓取的 19 行里，**0 行是字幕**——全是 B站界面文字（"发送"、"2人正在看"、"已关闭弹幕"、播放量等）。

**但真正的结论不是"要加过滤规则"，而是"判据放错了地方"** —— 见 9.3。

**② Retina 降采样导致 OCR 精度打折（已确认并修复）**

`CGDisplayPixelsWide()` 在缩放显示模式下返回的是**点**而非**像素**，导致算出的缩放系数是 1.0x，把 Retina 画面**降采样了一半**——OCR 精度白白损失。

修复：改用 `CGDisplayCopyDisplayMode(id).pixelWidth`。**实测已确认修复生效**：真实像素 2940 宽 → 缩放 2.00x，抓取输出 2940×1912（原生 Retina）。

### 9.3 设计原则修正：判据交给用户，不交给规则

最初想用一堆规则来判断"什么算字幕"。这条路被否掉了：

| 写死的东西 | 换个场景会怎样崩 |
|---|---|
| 抓屏幕底部 28% 这条带 | 全屏 / 窗口 / 不同平台，字幕位置都不一样 |
| 连续 N 帧相同 = UI | 弹幕在滚、进度条在跳，会误伤真字幕 |
| 汉字占比 > 0.5 算中文 | 一行里中英夹杂，直接判错 |
| 中英靠 y 坐标相邻配对 | 有的视频中英挤在同一行 |
| 成句靠"稳定 N 帧" | 短句、快节奏对话会漏 |

**每一处都是拍脑袋定的常数，换个视频就可能全崩。**

**修正后的原则：**

1. **范围由用户框选定义** —— 灵活度的真正来源是**框选**，不是规则。框到字幕那两行上，噪音天然就没有了。
2. **工具不预判** —— 框到哪就抓哪，抓到什么都原样沉淀，不加过滤。
3. **去留由用户标记** —— 看到噪音点一下排除，工具记住。规则是用户教出来的，不是写死的。

这也回到了最初的定义：**"只要是识别到的文本都沉淀下来"**。

**spike 已按此改写**：写死的区域删掉了，换成真正的拖拽框选（`RegionPicker.swift`，同时它就是 MVP 的 M1 功能）；静态/动态分析降级为**纯观察输出**，不参与任何行为。

### 9.4 踩坑记录：跑过 AppKit 事件循环后，进程静默 `exit(0)` ⚠️

**现象**：框选完成后，进程跑几帧就**回到 shell 提示符**，退出码 `0`，**没有任何报错**。

**排查过程**（全部用 **30 帧长跑**，见下方教训）：

| 试验 | 结果 |
|---|---|
| `--full` / `--rect`（完全不碰 AppKit） | ✅ 正常 |
| 建遮罩窗口，**不跑事件循环** | ✅ **30/30 帧** |
| 建遮罩窗口，**跑事件循环** | ❌ **8–12 帧后必死** |
| 摘掉 `activate` | ❌ 死得更快（1 帧） |
| 摘掉拆窗（teardown 全空） | ❌ 12 帧 |
| 挂 `NSApplicationDelegate`，`applicationShouldTerminateAfterLastWindowClosed` 返回 `false` | ❌ 拦不住 |

**根因**：`NSApplication.nextEvent`（AppKit 的事件循环）与 `@main async` 的主队列驱动**无法共存**。跑过之后，进程会在几秒后静默 `exit(0)`——表现为「抓屏抓了几帧就没了」，极易误判成抓屏或 OCR 的问题。

**修法**：把框选**丢给一个短命子进程**（`--pick-only`）：子进程建遮罩、跑事件循环、把结果打到 stdout、然后自己退出；主进程从头到尾**不碰 AppKit**。见 [`spike/Sources/SubtitleSpike/RegionPicker.swift`](../spike/Sources/SubtitleSpike/RegionPicker.swift) 顶部注释。

**⚠️ 教训：短测试会给出错误结论。**
第一轮排查时我用 `--frames 2` / `--frames 4` 验证，得出「拆窗是元凶」的结论并据此改了代码——**是错的**。故障是**延迟发作**的，跑 4 帧根本触发不了。**必须跑到足够长（30 帧）才看得见。** 后来给 picker 加了 `--autopick`，让这条路径可以自动化长跑，才真正修掉。

**对正式版的意义**：这是**命令行工具特有**的坑（裸 `NSApplication` + async main）。正式版是正常的 `.app` + `NSApplicationMain()`，不会遇到。

### 9.5 框选实测结果（2026-10-05，27 帧真实剧集）

**框选区域 428×43 点 → 输出 856×85 像素。这一版是 spike 的最终结论。**

#### 数据

| 项 | 实测 | 结论 |
|---|---|---|
| **每帧行数** | **2 行**（全屏时 19 行） | ✅ **框选彻底解决噪音**，M1 的价值被证实 |
| 杂讯 | 26 帧里仅 1 帧多出 1 行 | 是画面右上角 UI（`y=0.047 x=0.871`），在字幕带之外 |
| 空帧 | 27 帧里 1 帧 0 行 | 转场/黑场，**天然的分句点** |
| **中文 y** | 0.042 – 0.140（**波动大**） | ⚠️ 见下方 ① |
| **英文 y** | 0.562 – 0.605（**稳定**） | 中英 **gap 极大**（0.14 vs 0.58） |
| 抓屏 | 28–51 ms | ✅ |
| OCR | 18–177 ms（多数 30–100） | ✅ 首帧偏慢 |
| 端到端 | **约 100 ms（≈10 fps）** | ✅ 远超需求（一句持续数秒） |
| 中文识别 | `谢谢夸奖` / `你是个很棒的写手` / `这种天分很罕见` / `能得到你的赞美 对我来说意义重大` | ✅ **质量很高** |
| 中文 confidence | 常 1.00，偶尔 0.30–0.50 | |
| 英文 confidence | **常年 0.30–0.50** | ⚠️ 见下方 ③ |

#### 五条设计结论（直接决定 M3/M6 怎么写）

**① 配对用「行序 + 语种」，不要用绝对 y 阈值**

中文 y 在同一句话里能从 0.116 漂到 0.042（**同一句 "能得到你的赞美…" 连续 5 帧漂了 0.074**），而英文稳定在 0.58。所以「中英相差 N 个像素」这类阈值会很脆。

**但中英的上下顺序 100% 稳定，且 gap 极大。** 正确做法：同一帧内按 y 排序，**取「中文行在英文行上方」这个结构关系**配对，而不是卡某个 y 阈值。

**② 去重必须模糊匹配，不能用字符串相等**（原计划就是错的）

同一句字幕跨帧的真实差异：

| 帧 | 识别结果 |
|---|---|
| 1 | `Yeah. The only thing I've ever burned` |
| 2 | `Yeah. The only thing I've eyer burned` |
| 3 | `Oh, uh, yeah. Oh, thank you so much.` |
| 2 | `-oh, uh. yeah. Oh, thank ygu so much.` |
| 23 | `- Honestly, l was like obsessed ... when lwas ten` |
| 26 | `- Honestly, I was like obsessed ... when I was ten` |

差异来源：**前导 `- ` 有无、大小写、标点、`I`↔`l`、`m`↔`n`、`you`↔`ygu`**。

→ 必须用**编辑距离 / 相似度阈值**判定"是否同一句"。**原先「连续 N 帧文本相同」的规则会完全失效**——同一句话永远对不上，会被当成 N 句入库。

**③ confidence 不能当过滤阀**

英文 confidence **常年 0.30–0.50**，而它识别的内容是对的。中文杂讯 `开启画9` 的 confidence 也有 0.50。**两者区间重叠，用 confidence 切不出噪音。**

**④ 入库要取"最干净的那一帧"，不是第一帧**

同一句在不同帧质量不同（`-oh, uh. yeah.` vs `- oh, uh, yeah.`）。需要按**清洗后文本的质量**（或候选中位数/众数）选一个入库，而不是见到就写。

**⑤ 行首 `- ` 是说话人切换标记**

`- Honestly, ...` / `- You're an excellent joke writer.` —— 这是字幕的对话标记，对**分句**有价值，但入库前要清洗掉。

#### spike 的最终判定

| 待验证项 | 结果 |
|---|---|
| 框准之后还有没有噪音？ | ✅ **没有了**（19 行 → 2 行） |
| 中英能否稳定配对？ | ✅ **能**，用行序而非绝对 y |
| OCR 够不够快？ | ✅ **约 100ms / 10fps**，远超够用 |
| 有没有新发现的坑？ | ⚠️ **去重必须模糊匹配**、confidence 不可用 |

**技术链路全部验证通过，且拿到了 M3/M6 的具体设计约束。spike 使命完成。**

## 10. 竞品调研与定位（2026-10-05）

> star / 更新时间为 GitHub API 数据，截至 2026-10-05。

### 10.1 同款项目已经存在

| 项目 | 做了什么 | 许可证 |
|---|---|---|
| **[SwiftyCrow](https://github.com/PangMo5/SwiftyCrow)** 108★ | **技术栈与本项目完全一致**：ScreenCaptureKit + Vision + Apple Translation。框选区域 → 实时 OCR → 翻译 → 悬浮窗显示；区域内容变化即重新识别；支持竖排 CJK | AGPL-3.0 |
| **[screenTranslate](https://github.com/hcmhcs/screenTranslate)** 80★ | 其 **Live Translate (Beta)** 明确针对「视频/直播里烧录的字幕」，译文以条状栏跟随字幕更新。更新频繁 | GPL-3.0 |

**结论**：「框选 → 实时 OCR → 旁边滚字幕」这条链路**已被社区验证可行**，不是未知数。

### 10.2 定位：要做的是它们没做的那一层

**两个项目都止步于「看懂」——没有任何一个做「去重成句 + 中英配对 + 全量沉淀 + 导出对照文本」。**

这恰好是本项目的核心价值（用户原话：*"把全字幕导出来作为资料背诵"*）。

> **反直觉但关键的结论**：本项目前期投入最大的部分（抓屏 / OCR / 悬浮窗）是**已被解决**的；而尚未动工的**成句 / 配对 / 导出**，才是社区空白、也是真正的差异化。

### 10.3 因「做成产品」而确定的约束

- **SwiftyCrow / screenTranslate 只作参考实现**（读思路），**不复用其代码** —— 强 copyleft（AGPL/GPL）与商业目标冲突。
- **可自由复用的**（许可证宽松，逻辑可抄）：
  - **[VideOCR](https://github.com/timminator/VideOCR)**（MIT）—— 运动检测跳帧、中英混排识别、置信度+相似度双重过滤
  - **[VSE](https://github.com/YANGUK/video-subtitle-extractor)**（Apache-2.0）—— 字幕区域检测
  - **[VideoSubFinder](https://github.com/SWHL/VideoSubFinder)** —— 帧去重的经典算法（较老）
  - **[aio-hub realtime-subtitle-ocr](https://github.com/miaotouy/aio-hub)** —— 去重灵敏度参数化、时间轴设计的架构参考

### 10.4 技术选型复核：维持原判

| 环节 | 结论 |
|---|---|
| 抓屏 | **保持 ScreenCaptureKit**。无需引入封装库（该生态最好的 [Aperture](https://github.com/wulkano/Aperture) 已于 2024-11 停更） |
| OCR | **保持 Vision**。字幕是**干净的水平印刷体**，正是 Vision 最强的场景（准确率最高、速度最快、内存 ~136MB）。PaddleOCR 的优势在「真实场景文字」（招牌/远景），本场景用不上，且 Mac 上是 CPU-only、慢约 20 倍、内存 ~4.3GB。**PaddleOCR 目前没有官方 CoreML 版本**，RapidOCR 的 CoreML EP 实测比 CPU 还慢 |
| 翻译 | **保持 Apple Translation**（社区主流）。macOS 26.4+ 可切 High fidelity（Apple Intelligence） |
| 悬浮窗 | 无统治级库，**自己写 NSPanel**（约 20 行） |
| 中文难例兜底 | 可选：加 **LiveText / `ImageAnalyzer`** 作为第二 OCR 后端（社区实测对中文常强于裸 `VNRecognizeTextRequest`，竖排更好） |

### 10.5 一个能少走弯路的提醒

**中英配对不要照搬跨字幕轨的时间轴对齐算法**（如 [DuoSubs](https://github.com/CK-Explorer/DuoSubs) 的 DTW + 滑动窗口）。本项目的中英是**同一帧里并排两行**，**按 y 坐标 / 行序分组**即可，比跨轨对齐简单一个量级。真正难的是**去重成句**和**噪音过滤**。
