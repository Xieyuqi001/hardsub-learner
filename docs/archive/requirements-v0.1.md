# 硬字幕学习工具 — 需求文档 v0.1

> 状态：需求澄清完成，技术调研完成，待关键实测确认后进入方案设计
> 日期：2026-10-05

---

## 1. 一句话定义

在任意播放器上看英文视频时，**实时把画面上的硬字幕抓成文本**，用一个可滚动的字幕稿悬浮窗呈现，支持中英分轨、收藏句子、导出中英对照资料。

核心差异点：**资源不受限**。不依赖 Netflix/YouTube 的原生字幕轨，因此可以拿任何自己喜欢的资源（网盘存的剧、B站视频）来学英语。

---

## 2. 目标与非目标

### 目标
以「我喜欢的资源」为输入，无侵入地积累可背诵的英语语料。

### 非目标（v1 明确不做）
- ❌ 不做播放器（用户接受用现有播放器 + 模拟按键）
- ❌ 不做视频下载 / 转码 / 资源管理
- ❌ 不做云同步、账号、社交
- ❌ 不做自动翻译（源视频已自带中英双语字幕，无需翻译）
- ❌ 不做逐词点击查词、生词本（v1 只到"句子"粒度）

---

## 3. 用户场景

我用 B站网页版 / 夸克网盘客户端看美剧，字幕是中英双语的硬字幕。

1. 打开工具，**框选画面上的字幕区域**（一次即可，之后按应用自动记住）
2. 悬浮窗开始实时显示识别到的字幕，按**剧本形式滚动**，最新一句高亮
3. 中英文分两行显示，**中文可以一键关掉**（练纯英文听力）
4. 遇到好句子，按快捷键**收藏**
5. 看完导出**中英对照纯文本**（全部 or 仅收藏），拿去背诵

## 4. 功能需求

### 4.1 v1 — 验证核心体验

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| **F1** | 区域框选与记忆 | 拖拽框选字幕区域；按「应用 + 窗口模式（全屏/窗口）」记忆 preset，下次自动应用 | P0 |
| **F2** | 实时 OCR | 定时抓取该区域并识别；画面未变化时跳过，避免空转耗电 | P0 |
| **F3** | 滚动字幕稿 | 置顶悬浮窗，按时间顺序累积显示已识别的句子；可上下滚动回看；当前句高亮并自动滚到底 | P0 |
| **F4** | 中英分轨与开关 | 按行分离中英文；支持"只英文 / 只中文 / 中英对照"切换 | P0 |
| **F5** | 去重与落盘 | 识别结果去重后持久化（含时间、来源、中英文本），为导出做准备 | P0 |
| **F6** | 收藏当前句 | 全局快捷键收藏"当前正在显示的句子"；收藏夹可查看、可取消 | P0 |
| **F7** | 导出 | 导出全部 / 仅收藏，**中英对照纯文本**（Markdown 或 txt），可按来源和日期分组 | P0 |

### 4.2 v2 — 增强

| 编号 | 功能 | 说明 |
|---|---|---|
| **F8** | 单句循环 / 随时回退 | 通过模拟键盘按键近似实现；精度约 ±1 秒（用户已接受） |
| **F9** | 遮挡中文硬字幕 | 可选开关：在视频画面的中文行位置盖一个色块，画面只剩英文。需要动态获取中文行的位置 |

### 4.3 关键设计约束

- **F3 是产品的灵魂**。硬字幕一闪而过，悬浮窗的价值就是**可回看上下文**——这是"看得爽"和"学得进"的分水岭。字幕稿的排版、滚动、高亮体验要重点打磨。
- **F7 几乎是白送的**：因为 F3 已经在积累字幕稿，导出只是换个序列化格式。
- **F4 的中文开关**只影响悬浮窗，不改变视频画面（除非启用 F9）。
- ⚠️ **F9 与抓屏有直接冲突**（见 R3）：遮挡色块本身会被 OCR 读成中文，必须用 SCContentFilter 把本 App 从捕获源里排除。

## 5. 关键技术决策（及理由）

| 决策 | 选择 | 理由 |
|---|---|---|
| 字幕获取方式 | **屏幕 OCR** | 字幕是**硬字幕**（烧在画面上、无法关闭），读字幕轨的路全部堵死，OCR 是唯一解 |
| OCR 引擎 | **Apple Vision（`VNRecognizeTextRequest`）** | 本地、免费、离线、无模型依赖；硬字幕字体规整、位置固定、对比度高，识别难度远低于自然场景文字 |
| OCR 等级 | **`.accurate`（强制）** | `.fast` 等级**完全不支持中文**。这是硬约束，直接锁定帧率上限（见 R6） |
| 抓屏方式 | **ScreenCaptureKit** | 系统原生，可精确指定捕获区域；窗口模式抓窗口、全屏模式抓显示器矩形 |
| 播放控制 | **模拟按键（CGEvent）** | 用户接受 ±1 秒误差，换取"什么播放器都能用"的通用性；避免自建播放器的巨大成本 |
| 句子的时间戳 | **由 OCR 文本变化的时刻推断** | 无法从硬字幕拿到真实时间轴；字幕文本变化的瞬间即新句起点，误差约 0.3–1 秒 |
| 悬浮窗 | **`NSPanel` + `.nonactivatingPanel` + `.fullScreenAuxiliary`** | 唯一能同时做到"置顶 + 不抢焦点 + 跨所有 Space + 覆盖全屏"的配方 |
| 技术栈 | 建议 Swift + SwiftUI（原生 macOS App） | ScreenCaptureKit / Vision 均为系统框架；用 Electron 需外挂 OCR，得不偿失 |
| 运行环境 | macOS 26（Darwin 25） | 最新 API 全可用 |

### 为什么不用视觉大模型（VLM）
Qwen3-VL 等模型的 computer-use / GUI grounding 能力是"让 AI 替你操作软件"的赛道。本工具**不需要模型去操作播放器**，只需要读字。用 VLM 做 OCR 是最贵、最慢、最不确定的解法。除非遇到极端花哨的艺术字，否则用不上。

### 为什么不用音频 ASR（已正式排除）
macOS 26 的 `SpeechAnalyzer` 中文能力很强（CER ≈ 7.97，本地实时），但它转写的是**音频里人说的话**，而本项目要的是**画面上的中英硬字幕**。看美剧时音频是英文台词，**ASR 拿不到中文字幕**；就算台词与硬字幕意思相同，措辞也可能对不上。ASR 唯一的优势是词级时间戳，但为此丢掉文本来源不划算。

## 6. 风险清单

| # | 风险 | 严重度 | 状态 | 说明 / 对策 |
|---|---|---|---|---|
| **R1** | **夸克/阿里云盘客户端无公开快捷键** | 🔴 极高 | **必须实测** | B站 `←→`=5秒、百度网盘 `←→`=5秒（已确认）；夸克/阿里云盘官方文档缺失。对策：按键映射做成可配置，别硬编码 |
| **R2** | **目标播放源抓屏得到黑屏** | 🔴 高 | **必须实测** | DRM 主动打黑（Netflix 等）不可绕过；另有时序陷阱：切到其他 Space 后硬件合成视频变黑，且 `SCFrameStatus` 仍报正常，无法据此判断 |
| **R3** | **自捕获污染：悬浮窗/遮挡色块被自己录进 OCR** | 🟠 中高 | 已知，有解 | SCK 抓的是合成后的帧缓冲。必须用 `SCContentFilter` 排除本 App；注意 macOS 15+ 后 `sharingType = .none` 已失效，不能靠它 |
| **R4** | macOS 26 上悬浮窗覆盖全屏 Space 配方可能失效 | 🟠 中高 | **必须实测** | 老配方 `level=.screenSaver + canJoinAllSpaces` 在 macOS 26 有失效报告，需实机验证新配方 |
| **R5** | 透明窗口点击穿透在 macOS 26 有回归 | 🟠 中 | 必须实测 | 26.3 RC 报告整窗拦截鼠标（连不透明区也拦）。可实测 + 用像素 alpha 动态切 `ignoresMouseEvents` |
| **R6** | 中文强制 `.accurate` → 帧率锁定个位数 | 🟡 中 | 已知，可接受 | `.accurate` 实测约 100–300ms/帧。字幕每句持续数秒，**够用**——不要按 60fps 设计 |
| **R7** | 屏幕录制权限每次重编译后丢失 | 🟡 中 | 已知，有解 | ad-hoc 签名的权限绑定 cdhash，每次编译都变。开发期改用 **Apple Development 证书** + 固定 Bundle ID/路径；卡死时 `tccutil reset` |
| **R8** | 模拟按键的权限与发行渠道冲突 | 🟡 中 | **需决策** | CGEvent 需 PostEvent 权限（系统设置里显示为"辅助功能"）、要求播放器在前台；且用 CGEvent 有 **App Store 2.4.5 拒审**先例。想用 AX 读进度条则**不能开沙盒**。发行渠道要提前定 |
| **R9** | 全屏 ↔ 窗口切换导致框选区域失效 | 🟢 低 | 已知，有成熟做法 | 按「应用 + 窗口模式」记忆 preset；窗口模式抓窗口时区域自动跟随 |
| **R10** | 弹幕/水印混入 OCR；字幕碎片化或漏识别 | 🟢 低 | 需设计 | 时序去重（相邻帧 Jaccard/Levenshtein）+ 置信度阈值过滤 + 稳定判据 |
| **R11** | 多显示器 Retina 坐标换算错误 | 🟢 低 | 已知，有标准修法 | AppKit 左下原点/全局坐标 vs SCK 左上原点/屏幕局部 + 像素换算。先只支持主屏可规避 |
| **R12** | 悬浮窗占地方 | 🟢 低 | 设计权衡 | 用户选的是"整个滚动字幕稿"，可调大小/透明度/位置 |

## 7. 验收指标（待与实现对齐）

- OCR 端到端延迟：**< 500 ms**（字幕出现到悬浮窗显示）
- OCR 帧率：**2–5 fps**（受 `.accurate` 约束，这是设计前提不是缺陷）
- CPU 占用：**< 10%**（单核，持续运行）
- 字幕召回率：**> 95%**（硬字幕应能达标）
- 中英分行准确率：**> 98%**

## 9. 现有工具调研结论（2026-10-05）

### 9.1 一句话结论

**没有现成工具能满足全部需求。** 但有两块基石可以直接复用。

### 9.2 三个阵营，各有各的死穴

| 阵营 | 代表 | 死穴 |
|---|---|---|
| **实时屏幕 OCR 工具** | SwiftyCrow、screenTranslate、Transcendia、Translix | 只显示"当前这一句"，**没有滚动字幕稿、没有收藏、没有分轨导出** |
| **硬字幕提取工具** | VSE、SubtitleEdit、VideOCR | **批量离线，必须本地文件**，无法处理网盘在线播放 |
| **看剧学英语工具** | Language Reactor、asbplayer、mpvacious | **全部依赖软字幕轨，遇到硬字幕直接失效** |

第三类值得注意：这个赛道很成熟（asbplayer 的"自动暂停 + 单句循环"、譯魔 WizSubs 的"字幕面板 + 点击跳转 + 收藏句子"、CapTran 的"双语滚动历史 + 导出 srt"交互都做得很到位），**但因为它们全都绑死软字幕，没有一个能碰硬字幕**。这恰好确认了本项目的空白区是真实存在的。

### 9.3 两个候选底座

|  | **screenTranslate** | **SwiftyCrow** |
|---|---|---|
| 仓库 | hcmhcs/screenTranslate | PangMo5/SwiftyCrow |
| 许可证 | **GPL-3.0** | **AGPL-3.0** |
| 技术栈 | Swift 6 + SwiftUI + SwiftData | SwiftUI + TCA + Tuist |
| 系统要求 | macOS 15+ | macOS 26+ |
| 抓屏 / OCR | ScreenCaptureKit + Apple Vision | ScreenCaptureKit + Apple Vision |
| 中文 | 支持，自动检测源语言 | **强项**，明确支持 CJK 竖排/多栏/文档结构 |
| 已具备 | 框选区域实时 OCR、悬浮条、**可搜索的历史** | 框选区域实时 OCR、悬浮层、CJK 优化 |
| **缺什么** | 滚动字幕稿、中英分轨+开关、收藏当前句、中英对照导出 | 同上，且**无历史记录** |
| 备注 | 明确面向"烧进视频的字幕"（Live Translate Beta） | CJK OCR 质量可能更好 |

**许可证提示**：两者都是 copyleft。**自己用无所谓；若要发布或开源，改 screenTranslate 会要求你也以 GPL-3.0 开放，改 SwiftyCrow 的 AGPL 约束更强**（网络服务化也会触发）。需要提前决定。

### 9.4 可直接复用的开源件

- **抓屏 + OCR 示例代码**：[kapt](https://github.com/sonpiaz/kapt)（Swift 6 + ScreenCaptureKit + Vision，有独立的 Capture/ 和 OCR/ 目录）、[RegionShot](https://deepwiki.com/pardeike/RegionShot)
- **双语行分离**：用 Unicode 脚本匹配（`\p{Han}` vs `\p{Latin}`）+ 汉字占比打分 + 上下文平滑；若字号位置固定，直接按 boundingBox 的 y 坐标分离更省事
- **交互参考**：asbplayer 的单句循环/自动暂停、譯魔 WizSubs 的句子收藏 + 导出、CapTran 的双语滚动历史

### 9.5 确认的空白区（本项目的差异化）

1. 实时 OCR + **可滚动字幕稿历史**，当前句高亮 —— 所有实时工具都只显示当前一句
2. **中英分轨 + 中文行一键开关** —— 无人做
3. **一键收藏当前句 + 中英对照导出** —— 学习工具有收藏但依赖软字幕，实时工具有历史但无收藏导出
4. **网盘在线播放的硬字幕实时 OCR** —— 批量工具做不到，实时工具未验证
5. 由 OCR 字幕变化驱动的**单句循环** —— 现有实现只对软字幕生效

## 10. 技术可行性调研结论（2026-10-05）

### 10.1 总体判断

**方案整体可行**，但有五条必须实测的未知项，以及几条会直接改变设计的技术事实。

### 10.2 会改变设计的硬事实

**① 中文 OCR 必须用 `.accurate`，帧率因此锁定在个位数 fps**
`VNRecognizeTextRequest` 的 `.fast` 等级**完全不支持中文**（支持列表只有 en/fr/it/de/es/pt-BR）。要用中文只能 `.accurate`，实测约 100–300ms/帧。**但字幕每句持续数秒，2–5 fps 完全够用。** 这决定了架构：OCR 放后台队列、对结果做时序去重，而不是追求高帧率。另外，只送"字幕横带"这个小 ROI 进去，实际耗时大概率更低（需实测）。

**② 中英混排的正确写法**
```swift
let req = VNRecognizeTextRequest()
req.recognitionLevel = .accurate                          // 中文强制；fast 不支持中文
req.recognitionLanguages = ["zh-Hans", "zh-Hant", "en-US"] // 中文必须排在前面
req.usesLanguageCorrection = true
req.customWords = ["角色名", "专有名词"]                    // 提升专名准确率
```
关键限制：**English 是唯一能与中文配对的语言**；**`automaticallyDetectsLanguage` 对中文无效**，必须显式指定。

**③ 抓窗口与抓全屏是两种模式，都要做**
- 窗口播放 → 抓窗口（`SCContentFilter(desktopIndependentWindow:)`），用户拖动窗口时区域自动跟随，什么都不用重算
- 全屏播放 → 抓显示器 + `sourceRect`
- 坐标系有三处错位（AppKit 左下原点/全局 vs SCK 左上原点/屏幕局部；还有点与像素的换算）。**单主屏时 bug 会被隐藏，接了副屏必然暴露。**

**④ 悬浮窗会被自己录进去（直接威胁 F9）**
ScreenCaptureKit 抓的是**合成后的帧缓冲**，所以你的悬浮窗、以及 F9 用来遮挡中文的色块，**都会被 OCR 读回来**——你盖住中文，OCR 却识别出中文，逻辑直接崩掉。
对策：用 `SCContentFilter` 的 `excludingApplications` / `excludingWindows` **排除本 App**。注意 macOS 15+ 之后 `sharingType = .none` 已经不能阻止捕获了。

**⑤ 悬浮窗的配方**
`NSPanel` + `styleMask: [.borderless, .nonactivatingPanel]` + `level = .floating` + `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]` + `contentView = NSHostingView(...)`。`.fullScreenAuxiliary` 是能覆盖全屏视频的关键。

### 10.3 实测出来的好消息

- **B站网页版** `←` `→` = **5 秒**（长按可加速），`空格/K` 暂停，`F` 全屏 ✅
- **百度网盘** `←` `→` = **5 秒** ✅
- 方向键的虚拟键码**与键盘布局无关**，不用担心不同键盘布局的问题
- 网盘 Mac 客户端被指为 **webview 内核**，播放走标准 HTML5 `<video>` + 硬件解码，**大概率不触发 DRM 打黑**（需实测确认）

### 10.4 模拟按键这一环的完整图景

- CGEvent 走的是 **PostEvent 权限**（系统设置里显示在"辅助功能"行），且**事件发给当前最前台 App**——播放器必须在前台
- `MPNowPlayingInfoCenter` **读不到**第三方播放器的进度（只能写自己的），排除
- **`AXUIElement` 读进度条滑块**（`AXValue` + `AXMin/MaxValue`）理论可行，**若能读到，单句循环的精度会大幅提升**（从"靠 OCR 推断"变成"读真实播放位置"）。但：能不能读到取决于播放器是否把控件暴露到 AX 树；且 AX 方案**不兼容沙盒**
- **实测方法**（针对夸克/阿里云盘/百度网盘客户端）：
  1. 让播放器获得焦点，依次试 `←` `→`、`J`/`L`、`,`/`.`、`Shift+←/→`、`Cmd+←/→`，看进度条跳多少
  2. 用 Accessibility Inspector 查看播放器窗口的 AX 树，确认进度条角色（AXSlider/AXProgressIndicator）和 `AXValue` 是否可读
  3. 记录普通播放与全屏下快捷键是否一致

### 10.5 字幕区域自动定位（v1 之后的增强）

不用手工框选也可以：**取画面高度 55%–85% 的横带**（85% 以下通常是推广条/水印），再用**时序特征**锁定——字幕的特征是"位置固定、内容多变、持续时长最长"。用"相同文本的累计显示时长"就能把水印/台标/标题过滤掉。业界有做到 83% 准确率的成熟 pipeline。

v1 建议还是**手工框选 + 记忆 preset**，够了。

## 附录 A：澄清过程中排除的方案

| 方案 | 为什么排除 |
|---|---|
| 浏览器扩展 | 用户主要在网盘**客户端**看，扩展覆盖不到；且已选定桌面悬浮窗形态 |
| 自建播放器 | 失去"悬浮在任意播放器上"的通用性；网盘流还要处理登录态 |
| 音频 ASR（Whisper / SpeechAnalyzer） | 拿不到"画面上显示的字幕"，尤其是中文字幕；见第 5 节 |
| 读字幕轨 / 字幕文件 | 前提是软字幕，与"硬字幕"的事实不符 |
| 批量离线提取（下载后再处理） | 用户是在线看，没有本地视频文件 |
| 视觉大模型（Qwen3-VL 等） | 解决的是"替你操作软件"，不是"读字"；最贵最慢 |
